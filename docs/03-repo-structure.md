# Repo Structure

Delivery is the shim (doc 06). The layout below is the corpus, manifest,
and tooling structure the shim builds share; the "Host CLI integration
points" at the end are the sketch for a CLI adopting the contract
natively — the upstreaming direction, not how this repo ships skills.

## Layout

```text
embedded-skills/
├── README.md                  # what this repo is, how to contribute a skill
├── docs/                      # this design package
├── skills/                    # the embedded skill corpus
│   ├── _template/
│   │   └── SKILL.md           # starting point for new skills
│   ├── commit-flow/
│   │   ├── SKILL.md
│   │   └── references/
│   │       └── edge-cases.md
│   └── ...
├── manifest.json              # generated index of the corpus (do not edit)
├── tools/
│   ├── build-manifest         # regenerates manifest.json from skills/
│   └── lint-skills            # runs the `cli skills check` rules against the repo
├── cli/                       # reference integration for a host CLI
│   └── skills.go              # skills subcommand (+ optional --skill) (sketch)
└── tests/
    └── manifest_test.go       # manifest freshness, schema, drift checks
```

Design decisions behind the layout:

- **One directory per skill, `SKILL.md` at its root.** Agents trained on
  skill directories recognize this layout; it also leaves room for support files
  without inventing a packaging format.
- **`skills/` is CLI-agnostic.** The corpus describes workflows, not
  implementation. The host CLI embeds it; nothing in `skills/` imports CLI
  code.
- **`manifest.json` is generated, never hand-edited.** It is the index the
  binary reads at runtime; generating it removes a class of human error.
- **`tools/` holds repo automation** (manifest generation, lint) so CI can run
  them without a dev environment.

## manifest.json

Generated by `tools/build-manifest` at build time:

```json
{
  "version": 1,
  "target": "cli",
  "target_version": "1.4.0",
  "version_probe": {"args": ["--version"], "regex": "(\\d+\\.\\d+(\\.\\d+)?)"},
  "skills": [
    {
      "name": "commit-flow",
      "path": "skills/commit-flow/SKILL.md",
      "description": "Stage, review, and land one atomic change",
      "level": "beginner",
      "tags": ["vcs", "commit"],
      "commands": ["status", "diff", "add", "commit"],
      "prerequisites": [],
      "next": ["pr-flow"],
      "checksum": "sha256:9f2c1a..."
    }
  ]
}
```

`checksum` lets CI detect a stale manifest and lets the binary verify the
embedded corpus at startup (cheap, catches build mistakes). Checksums do not
stop tampering — the manifest ships inside the same artifact it verifies — so
releases are signed (cosign/minisign) with checksums published alongside; a
shim standing in front of a real CLI is a high-trust install, and users must
be able to verify it (see `09-implementation-and-evals.md`).

## Embedding: skills ship inside the binary

The corpus is compiled in at build time, not read from disk at runtime. That
is the single most important structural decision: **a skill can never describe
a CLI it does not match**, because both come from the same build.

Go sketch (the reference integration):

```go
import "embed"

//go:embed skills manifest.json
var corpus embed.FS

func listSkills() ([]SkillMeta, error) {
	data, err := corpus.ReadFile("manifest.json")
	if err != nil {
		return nil, err
	}
	var m Manifest
	if err := json.Unmarshal(data, &m); err != nil {
		return nil, err
	}
	return m.Skills, nil
}

func loadSkill(name string) (string, error) {
	// look up path in manifest, read from corpus, return verbatim
}
```

Equivalents: `include_bytes!` / `rust-embed` in Rust, bundling in Node/TS.
The mechanism differs; the invariant does not — corpus and binary are one
artifact.

## Versioning

- Skills are versioned with the CLI, not independently. A skill change is a
  CLI change and rides the same release.
- `manifest.json` records the target name and version it was generated
  against; CI fails if the checked-in manifest is stale relative to
  `skills/`. The schema is shared with the shim layout
  (`06-shim-pattern.md`): the native case sets `target` to the CLI's own
  name.
- The `--json` output schemas carry `"version": 1` (see `01-cli-surface.md`);
  bump on breaking changes.

## CI checks

1. `tools/build-manifest` produces no diff (manifest is fresh).
2. `tools/lint-skills` passes (all rules in `02-skill-format.md`).
3. `tests/manifest_test.go` passes: schema valid, names unique, checksums
   match, every `commands` path resolves in the CLI's command tree, and every
   flag used in a skill body exists on that command.
4. Binary smoke test: `cli skills` and `cli skills <name>` run against the
   embedded corpus in a clean environment (no `skills/` directory on disk).
5. Golden-file tests: rendered catalog and `--json` output for fixture skills
   compared byte-for-byte, so renderer changes are reviewable diffs.

## Host CLI integration points

The host CLI adds two things, both thin:

1. A `skills` subcommand backed by the embedded corpus (list / show / search /
   export / check) — the canonical surface.
2. Optionally, a persistent `--skill <name>` flag that prints delimited
   skill blocks before dispatching to the command. Non-canonical (doc 01);
   a host may omit it and lose nothing from the probing contract.

Everything else — parsing frontmatter, validating, rendering — lives
behind those surfaces. There is no usage tracking in v1.
